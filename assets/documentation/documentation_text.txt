SCOREX
ABOUT US
Cricket scoring, simplified.
ScoreX is an Android cricket scoring application created to make live cricket scoring
faster, clearer and easier to manage. From match setup to the final scorecard, ScoreX
brings the essential scoring workflow into one mobile application.
Who We Are
We are the team behind ScoreX, an Android-based cricket scoring project focused on combining practical live
scoring with useful match analysis. The application was developed around the real needs of a scorer: quick delivery
entry, automatic statistics, clear innings information and an easy way to review the match later.
ScoreX is designed as a local-first application. The current version does not depend on a traditional database or
cloud service for ordinary scoring. Match history, application settings and generated scorecard PDFs are handled
using local Android/Java storage mechanisms.
Our Vision
Our vision is to build a cricket scoring experience that feels simple during a live match but becomes powerful when
the match is finished. A scorer should be able to concentrate on the game instead of manually calculating every
statistic.

01. Executive Summary
ScoreX is an Android cricket scoring application built to manage a match from initial setup through live delivery
entry, innings management, statistics, scorecard review, graphs, local match history and PDF scorecard generation.
The central design idea is delivery-level state. A single delivery can affect the team score, batsman runs, balls,
bowler statistics, legal-ball count, strike, partnership and wicket state. ScoreX keeps these related changes
coordinated through its scoring/model layer rather than treating the score as a single text value.
The current project is a local Android application. It does not contain a
traditional relational database or cloud backend in the supplied source. Match
history uses Java serialization, settings use SharedPreferences, and generated
PDFs are kept locally.

02. Problem Statement, Objectives & Scope
Problem Statement
Manual cricket scoring requires continuous calculations and synchronized tracking. When a wide, no-ball, wicket,
partnership change or run-out occurs, several statistics may need to change at the same time. A small mistake can
therefore propagate into the scorecard and final result.
ScoreX addresses this by recording delivery events and maintaining structured information for players, bowlers,
overs, partnerships and innings.
Objectives
• Provide an easy-to-use Android interface for live cricket scoring.
• Reduce repetitive manual calculations during matches.
• Maintain consistent batting, bowling, partnership and innings information.
• Provide a structured scorecard for match review.
• Provide graphs for visual scoring analysis.
• Store completed matches locally for later review.
• Generate shareable PDF scorecards.
Scope
The current scope covers local match scoring and review. It includes match setup, live scoring, special deliveries,
wickets, innings transitions, result calculation, scorecard, graphs, history, settings and PDF export. It does not claim
cloud synchronization, online accounts or a remote database.

Why Delivery-Level State Matters
A cricket score is not enough by itself. For example, a No Ball + 4 requires the team total, batsman runs, extra total
and ball legality to remain consistent. A Run Out + 2 similarly requires both the wicket and completed runs. ScoreX's
model-oriented approach supports this multi-value update.

06. Detailed Cricket Scoring Rules
Normal Delivery
A normal scoring action records batsman runs and contributes to the legal-ball count according to the delivery state.
Wide
Wide is an extra. The project contains configurable wide behavior, including the configured run value and
re-ball/legal-ball behavior.
No Ball
No Ball records the no-ball extra separately from batsman runs. The project contains configurable no-ball behavior.
Bye
Bye adds to team extras without adding those runs to the batsman's personal run total.
Leg Bye
Leg Bye adds to the appropriate team extras category without becoming batsman runs.
Wicket
A wicket is recorded on the delivery and related wicket/dismissal information is updated.
Run Out
Run Out can include completed runs. The completed runs are retained rather than discarded when the wicket is
recorded.
Undo
Undo reverses the latest delivery and the related scoring state.
Over
Legal deliveries advance the over state according to the scoring rules; special deliveries can affect the legal-ball
count.
Innings
The first and second innings are maintained separately so the chase and final result can be evaluated.

07. Scorecard, Graphs & PDF System
Scorecard
The Scorecard is designed as the main review screen after or during an innings. Its information is organized around
cricket concepts rather than a generic data table.
Section
Information
Batting
Player, runs, balls, boundaries and strike rate.
Extras
Total extras and categories.
Bowling
Overs, maidens, runs, wickets and economy-related values.
Fall of Wickets
Wicket sequence with score/over context.
Partnerships / Overs
Supporting innings and over review.
Graphs
GraphsActivity provides visual analysis rather than another table. The project includes runs-per-over, run-rate and
innings-comparison concepts. The innings comparison is intended to show cumulative scoring for both innings, with
wicket events marked at the relevant scoring position.
Graph Design Goals
• Keep over labels readable and avoid overlapping text.
• Use cumulative score as the main comparison line.
• Place wicket markers on the actual score line rather than floating away from it.
• Make both innings visually comparable even when their lengths differ.
• Keep the graph useful for a quick cricket-style match review.
PDF Scorecard
The PDF output converts scorecard information into a permanent/shareable document. A good PDF should use
consistent typography, spacing, section hierarchy, page breaks and table widths so that long names and multiple
innings do not collide.

08. Data Storage, Privacy & Constraints
Storage Architecture
The current ScoreX project does not use SQLite, Room, Firebase, MySQL or another traditional database layer.
Instead, it uses local Android/Java storage mechanisms.
Data
Mechanism
Purpose

Java serialization (.ser)
Save/load/delete SavedMatch objects.

SharedPreferences
Store application/scoring preferences.

Privacy
• Ordinary scoring information remains on the device.
• No cloud synchronization is required for normal scoring.
• Sharing a PDF uses Android's sharing mechanism.
• Clearing application data can remove local history/settings/PDF data.
Constraints
• No remote database or account system in the supplied project.
• No built-in multi-device collaboration.
• Local storage capacity limits retained history/PDFs.
• The application is currently documented as Version 1.0.
